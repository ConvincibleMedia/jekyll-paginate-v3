# jekyll-paginate v1 Behaviour Contract and Compatibility Gap Analysis

This document is based on direct review of the vendored v1 source in `v1/`.

## v1 expected behaviour (from code)

### 1) Activation conditions

v1 pagination runs only when both are true:

- `site.config['paginate']` is not `nil`
- `site.pages.size > 0`

Source: `v1/jekyll-paginate/pager.rb` (`pagination_enabled?`).

### 2) Template page selection

v1 selects exactly one template page:

- Candidate must be `index.html`
- Candidate directory must be in the hierarchy between site `source` and `dirname(paginate_path)`
- If multiple candidates match, choose the one with the longest path (`two.path.size <=> one.path.size`)

Source: `v1/jekyll-paginate/pager.rb` (`pagination_candidate?`, `in_hierarchy`), `v1/jekyll-paginate/pagination.rb` (`template_page`).

### 3) Content paginated

v1 paginates only this list:

- `site.site_payload['site']['posts']`
- with hidden entries removed: `reject { |post| post['hidden'] }`

Source: `v1/jekyll-paginate/pagination.rb` (`paginate`).

### 4) Number of pages and slicing

- Total pages: `(all_posts.size.to_f / per_page.to_i).ceil`
- Current page slice:
  - `init = (page - 1) * per_page`
  - `offset = min(init + per_page - 1, all_posts.size)`
  - `posts = all_posts[init..offset]`

Source: `v1/jekyll-paginate/pager.rb`.

### 5) Path semantics

- Page 1 path resolves to template page URL (`Pagination.first_page_url(site)`)
- Page 2+ path uses `paginate_path` with mandatory `:num` substitution
- `paginate_path` must contain `:num`; otherwise `ArgumentError`
- Returned pagination paths are forced to have a leading slash

Source: `v1/jekyll-paginate/pager.rb`.

### 6) Generated pages behaviour

For page 1:

- Attach pager to existing template page (`page.pager = pager`)

For page 2+:

- Create page clone: `Page.new(site, site.source, page.dir, page.name)`
- Attach pager
- Set output dir to paginated path (`newpage.dir = Pager.paginate_path(site, num_page)`)
- Append to `site.pages`

Source: `v1/jekyll-paginate/pagination.rb`.

### 7) Liquid contract exposed by v1

`Pager#to_liquid` returns these keys:

- `page`
- `per_page`
- `posts`
- `total_posts`
- `total_pages`
- `previous_page`
- `previous_page_path`
- `next_page`
- `next_page_path`

Source: `v1/jekyll-paginate/pager.rb`.

### 8) Error behaviour

- Raises if `page > total_pages`
- Raises if `paginate_path` does not include `:num`

Source: `v1/jekyll-paginate/pager.rb`.

## What compatibility mode in this gem currently does

### Configuration trigger and mapping

If `site.config['paginate']` is present:

- logs legacy mode notice
- disallows simultaneous new `pagination` config (raises)
- maps:
  - `paginate` -> `default_config['per_page']`
  - `paginate_path` -> `default_config['permalink']` (if provided)
  - `source` -> `default_config['legacy_source']`
- forces `enabled = true`, `legacy = true`

Source: `lib/jekyll-paginate-v2/generator/paginationGenerator.rb`.

### Legacy execution branch in v2

When `legacy` is true:

- build post list from `site.site_payload['site']['posts']`, excluding hidden
- call `model.run_compatability(...)`

Source: `lib/jekyll-paginate-v2/generator/paginationGenerator.rb`.

### Legacy template selection and page generation

`CompatibilityUtils` mirrors v1 selection logic and hierarchy checks, then:

- page 1: attach pager to template page
- page 2+: create `CompatibilityPaginationPage`, attach pager, set `dir` using legacy paginate path, append page via callback

Source: `lib/jekyll-paginate-v2/generator/compatibilityUtils.rb`.

### Pager object used

Compatibility mode uses v2 `Paginator` (not v1 `Pager`) initialised with:

- `per_page`
- template page URL as first page URL
- legacy permalink format
- empty `indexpage` and empty extension values

Source: `lib/jekyll-paginate-v2/generator/compatibilityUtils.rb`, `lib/jekyll-paginate-v2/generator/paginator.rb`.

Its liquid payload is a superset of v1 keys, including v1-compatible keys and additional keys like `page_path`, `first_page_path`, `last_page_path`, `page_trail`.

## Compatibility mismatches and improvement priorities

### Critical mismatch 1: compatibility mode is hard-disabled by date gate

`run_compatability` raises once date is on/after `2018-01-01`:

- `raise ArgumentError.new("Legacy ... compatibility mode has expired ...")`

As of today, this makes compatibility mode unusable in normal runs.

Source: `lib/jekyll-paginate-v2/generator/paginationModel.rb`.

Improvement needed:

- Remove hard expiry branch entirely.
- Keep optional warning logs, but do not block runtime.

### High mismatch 2: AutoPages runs even when legacy mode is selected

Generator calls `PaginateV2::AutoPages.create_autopages(site)` before deciding legacy/non-legacy path.

v1 has no autopages subsystem. Running autopages during legacy mode can alter `site.pages` and potentially affect template candidate selection or produce extra generated pages that v1 would never produce.

Source: `lib/jekyll-paginate-v2/generator/paginationGenerator.rb`, plus TODO note in `lib/jekyll-paginate-v2/autopages/autoPages.rb`.

Improvement needed:

- Skip autopages entirely when legacy mode is active.

### Medium mismatch 3: extra `autogen` marker on compatibility-generated pages

Compatibility pages set:

- `newpage.data['autogen'] = "jekyll-paginate-v2"`

v1 does not set this field. This is usually harmless, but it is still observable behaviour divergence for templates/plugins that inspect page data.

Source: `lib/jekyll-paginate-v2/generator/compatibilityUtils.rb`.

Improvement needed:

- Either remove this in legacy mode, or guard behind explicit compatibility option.

### Medium mismatch 4: pager class identity differs from v1

Compatibility mode injects v2 `Paginator` object, not `Jekyll::Paginate::Pager`.

Liquid keys are backward-compatible (superset), but strict type checks in custom Ruby plugins could fail.

Source: `lib/jekyll-paginate-v2/generator/compatibilityUtils.rb`, `lib/jekyll-paginate-v2/generator/paginator.rb`.

Improvement needed:

- Prefer a dedicated legacy pager adapter object with v1-equivalent class name/shape, or explicitly document class-level non-compatibility.

### Low mismatch 5: legacy-mode warning/error text still references decommission timeline

Legacy messaging still refers to 2018 retirement, which is obsolete and misleading.

Source: `lib/jekyll-paginate-v2/generator/paginationModel.rb`.

Improvement needed:

- Update messaging to present-day behaviour and migration guidance.

## Final compatibility-mode rundown

In intent, compatibility mode is designed as a drop-in emulation of jekyll-paginate v1:

- trigger from legacy config (`paginate`, `paginate_path`)
- locate the same template page (`index.html` in hierarchy)
- paginate `site.site_payload['site']['posts']` with hidden posts removed
- generate page 1 on template and page 2+ into `paginate_path`
- expose expected paginator keys

In current implementation, there are two significant gaps versus true v1 behaviour:

1. Compatibility mode is effectively disabled by the hardcoded expiry check.
2. AutoPages side effects can occur before legacy processing, which v1 never did.

Removing the expiry gate and suppressing AutoPages under legacy mode are the two key changes needed to make behaviour materially align with v1 in modern runs.

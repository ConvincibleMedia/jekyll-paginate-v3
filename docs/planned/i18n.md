# First-class internationalisation

This document describes a planned, metadata-focused route towards making internationalisation (i18n) a first-class concept in Paginate V3.

It is a design specification, not a commitment to preserve the illustrative configuration syntax unchanged.


## Guiding star

Paginate V3 should understand that paginated items can belong to different locales. When i18n is enabled, pv3 should partition those items by locale, generate locale-specific pagination sets and write ordinary locale and identifier metadata onto every emitted index.

pv3 should not become a translation system. It should not extract locale information from source paths, infer equivalence between translated taxonomy values, construct language-switcher relationships, align item windows across locales, provide fallback content or implement locale-aware collation. Sites and other plugins can perform those tasks using the general metadata preserved on pv3's generated pages.


## Core invariants

An i18n-aware site provides metadata paths for two general facts:

* A **locale value** identifies the locale of a page, document or generated index.
* An **identifier** identifies the logical page or index represented. The identifier is independent of locale, allowing separate locale representations to use the same identifier.

The storage locations are site-specific. Examples include `locale` and `id`, or `meta.locale` and `meta.id`. pv3 should use the existing configurable frontmatter-path rules to read and write those locations.

Locale and identifier values must come from metadata. A site that derives either value from a source path or filename should use an earlier Jekyll hook or plugin to promote that information into metadata before pv3 runs. pv3 should not provide a second path-matching and capture system.

The following rules apply throughout the feature:

* i18n behaviour is opt-in.
* Locale is an outer variant axis. Ordinary groups and layouts expand within each locale.
* Locales are discovered from the items selected by a pagination template rather than from a configured site-wide list.
* A localised template contains only items from its locale.
* Every emitted index writes its locale and composed identifier to the configured general metadata paths.
* Locale and identifier data are not duplicated under `page.pagination`, `paginator` or another pv3-specific i18n payload.
* Ordinary paginator navigation remains locale-local by construction.
* Identifiers describe structural correspondence between generated indexes. They do not guarantee that independently paginated locale variants contain equivalent item windows.


## Configuration contract

The precise syntax can be refined during implementation, but the site configuration requires metadata paths for locale and identifier values:

```yaml
pagination:
  i18n:
    enabled: true
    locale: meta.locale
    id: meta.id
    unknown: und
```

The `locale` and `id` settings use the existing frontmatter-path syntax and equivalent-key behaviour for reads. Writes always target the exact configured paths so that generated pages expose one predictable general metadata schema.

`unknown` supplies a synthetic locale for items that lack locale metadata when other candidates do have locales. `und` is a useful default for sites using language tags, but the value should be configurable because pv3 does not require one particular locale-tag standard.

An individual pagination template may opt out when it intentionally combines locales:

```yaml
pagination:
  enabled: true
  i18n: false
```

No `i18n.variants` mode is required. Enabling i18n means that locale is respected by default.


## Locale values

Locale resolution should retain two internal representations:

* `raw`: the trimmed scalar metadata value supplied by the site, such as `en_GB`.
* `key`: a canonical internal value formed by lowercasing and slugifying the raw value, such as `en-gb`.

Comparisons, partitions and locale-specific configuration lookups use the canonical key. Emitted metadata uses the raw value chosen for that locale partition. Locale normalisation must remain independent of the template's ordinary `pagination.slugify` setting.

If several raw spellings canonicalise to one key, they belong to one partition. pv3 should select one raw spelling deterministically for generated metadata and report the inconsistent source values in diagnostics.


## Locale discovery and partitioning

Locale discovery occurs separately for each pagination template:

1. Resolve the template's configured item source.
2. Apply the template's ordinary non-locale filters.
3. Inspect the resulting candidates at the configured locale metadata path.
4. Determine the locale partitions.
5. Expand ordinary groups and layouts independently inside each partition.
6. Sort, offset, limit and paginate each resulting variant.

Discovery after ordinary filtering prevents a specialised template from producing locale variants solely because unrelated site content exists in those locales.

The template's own locale metadata affects partitioning:

* When the template has a locale, pv3 produces only that locale's partition. Candidate items without a matching canonical locale key are excluded.
* When the template has no locale, pv3 produces one variant for each locale discovered among its candidate items.

Missing candidate locale metadata follows these rules:

* If no candidate has a locale, pv3 retains one ordinary unsplit pagination set. Enabling i18n is therefore a no-op for a template whose selected content is entirely locale-neutral.
* If some candidates have locales and some do not, pv3 places the missing values in the configured synthetic `unknown` locale partition. This prevents locale-bearing and locale-less items from being mixed accidentally.
* If a localised template selects items without locale metadata, those items do not match its locale partition.

The synthetic partition behaves like any other locale variant. Its emitted indexes receive the configured synthetic locale value at the normal locale metadata path.

Locale partitioning must happen before group discovery. A category that exists only in one locale must not produce an empty group in another locale merely because it exists elsewhere.


## Locale-specific generated-template fields

Presentation-oriented generated-template settings may be either their existing scalar form or a map keyed by canonical locale:

```yaml
pagination:
  templates:
    generate:
    - items: posts
      frontmatter:
        meta:
          id: posts-index
      title:
        en: "Examples — page {{ num }}"
        fr: "Exemples — page {{ num }}"
      permalink:
        en: "examples/page/{{ num }}"
        fr: "exemples/page/{{ num }}"
      layout:
        en: examples
        fr: exemples
```

A scalar retains its current meaning and applies to every locale. A locale map selects the value for the active canonical locale key. An optional `default` entry may provide a fallback; otherwise a missing active-locale entry is a configuration error.

The initial locale-specific surface should remain narrow:

* `title`.
* `permalink`.
* Singular `layout`.
* Generated-template `content`.

Supporting locale maps for `layouts` should be deferred until pv3 has an invariant way to associate multiple output roles across locale-specific arrays. Query and window settings such as `items`, `filters`, `sort`, `offset`, `limit` and `per_page` remain common to every locale.

The active locale may also remain available to the placeholder pipeline. In presentation contexts `{{ locale }}` uses the raw value; in route contexts it uses the canonical key. This is a configuration convenience and does not require a public pv3 i18n payload.

Every resolved permalink must remain unique. pv3 should report destination collisions with the affected locale keys and source template.


## Generated index metadata

Every emitted pagination index writes ordinary metadata at the configured locations. For example:

```yaml
meta:
  locale: fr
  id: posts-index/group/category/examples/page/2
```

The locale value is the active partition's raw value. The identifier is composed from the source template's base identifier plus every invariant axis required to distinguish its emitted indexes:

* The base template identifier.
* The layout or output role when the template produces more than one kind of output.
* Each grouped-variant key in grouping order.
* The page number.

Locale is deliberately excluded from the identifier. The locale metadata is the separate value distinguishing representations of the same structural index.

The exact identifier encoding remains an implementation decision, but it must be deterministic, unambiguous and independent of localised presentation strings. Page one must receive a composed identifier just like every later page; it must not retain an identifier that could collide with the base template or another generated variant.

If the source template lacks a base identifier, pv3 should not derive one from its path. A locale-expanding template must instead supply the identifier at the configured metadata location. This keeps the metadata contract explicit and prevents output identity from changing when source files move.

Resolved layout names, translated titles and translated route segments must not become identifier components. When locale-specific layouts represent one common output role, their invariant configuration role identifies the variant rather than their different layout names.

Grouped variants require the same discipline. If `examples` and `exemples` are translated labels for one taxonomy concept, a site that needs matching cross-locale identifiers must expose and group on a shared taxonomy key. pv3 should not attempt to infer that translated group values are equivalent.

Two locale variants with the same composed identifier express structural correspondence, such as “page two of this generated index”. Because locale partitions are sorted and paginated independently, this does not assert that the pages contain identical logical items. Consumers decide whether structural correspondence is sufficient for their language-switching or SEO behaviour.


## Public page and paginator data

pv3 should not add any of the following:

```liquid
page.pagination.i18n
paginator.i18n
paginator.i18n.locales
```

Layouts and plugins read locale and identifier values from the configured ordinary page metadata. References to other index pages already expose those pages and therefore their general metadata.

The existing paginator API remains otherwise unchanged. Previous, next, first, last, trail and group navigation remain inside the current locale because each paginator is constructed from one locale partition.

pv3 does not build cross-locale page references, render language switchers or emit `hreflang` tags. Supplying consistent identifier and locale metadata is sufficient for another plugin or layout to provide those features.


## Sorting and alphabetic grouping

Locale-aware sorting and configurable collation providers are outside the scope of this feature. Enabling i18n should not alter the existing deterministic sorter.

The existing alphabetic buncher already performs best-effort Unicode decomposition and ASCII transliteration. This means Latin-derived characters such as `Å` can be bunched with `A` without a locale-specific provider.

Raw Unicode code-point ranges are not a general alphabetic-bunching model. Code-point order does not represent linguistic collation, decomposed characters and case variants complicate boundaries, and many scripts do not have useful alphabetic ranges that correspond to contiguous code points.

A future general grouping enhancement may retain non-Latin values by grouping on an initial Unicode letter or grapheme. Such behaviour should be described as deterministic Unicode grouping rather than locale-sensitive alphabetic collation, and should be designed independently of i18n pagination.


## Diagnostics

Debug reporting should include, per processed template:

* The template's raw and canonical locale, when present.
* The discovered locale partitions and their candidate counts.
* The number of candidates assigned to the synthetic locale.
* Inconsistent raw locale spellings that canonicalise to one key.
* Missing base identifiers on templates that require locale expansion.
* Missing locale-map entries for locale-specific settings.
* Destination and composed-identifier collisions.

A locale-bearing item does not require its own identifier merely to participate in pagination. Item identifiers and translation-family validation are outside pv3's locale-partitioning responsibility.


## Acceptance criteria

The feature is complete when all of the following hold:

* Flat and nested locale and identifier metadata paths use the existing frontmatter-path rules.
* Values promoted into metadata by an earlier hook behave exactly like source frontmatter.
* `en_GB`, `en-gb` and `EN_GB` select the same locale partition.
* A localised template paginates only items from its locale without an explicit locale filter.
* A locale-neutral template discovers locales from its filtered candidates and expands automatically.
* A template with no locale-bearing candidates retains its ordinary unsplit behaviour.
* Mixed locale-bearing and locale-less candidates produce a configured synthetic locale partition.
* Page, named-collection, `all` and `everything` item searches behave identically with respect to locale partitioning.
* Grouped and layout variants never escape their locale partition.
* Locale-specific `title`, `permalink`, `layout` and generated content resolve for the active locale.
* Every emitted page or document writes locale and composed identifier values to the configured general metadata paths.
* Composed identifiers distinguish grouped variants, output roles and page numbers without including locale or localised presentation strings.
* All ordinary paginator navigation remains locale-local.
* No pv3-specific i18n payload is added to pages or paginator drops.
* Explicitly opted-out templates and sites without i18n enabled preserve current behaviour.
* Existing V1 and V2 compatibility behaviour remains unchanged.


## Compatibility and migration

* `pagination.i18n` is a new opt-in configuration area.
* Do not reuse `pagination.locale`; V2 compatibility already interprets that key as a legacy filter shortcut.
* Existing explicit `filters` and `group: locale` configurations continue to work.
* Enabling i18n should not reinterpret a generic `locale` filter as the configured locale metadata path.
* Existing paginator keys remain unchanged.
* No new runtime dependency is required.
* Sites currently encoding locales or identifiers in paths must promote those values to metadata before pv3 runs.


## Internal shape

The likely internal components are:

* A metadata context that reads locale and base identifier values through the existing frontmatter-path abstraction.
* A nested metadata writer that assigns emitted locale and identifier values at the exact configured paths.
* A locale partition axis integrated with the existing group and layout variant expansion.
* Locale-map resolution for the narrow set of presentation-oriented generated-template fields.
* A deterministic identifier composer for grouped variant, output-role and page-number components.

Locale partitioning enters after the common candidate query and before ordinary variant expansion:

```text
resolve source template metadata
  -> resolve candidate items
  -> apply ordinary filters
  -> discover or select locale partitions
  -> expand groups and layouts within each locale
  -> resolve locale-specific presentation
  -> sort
  -> offset and limit
  -> build page windows
  -> compose identifiers
  -> emit indexes with general locale and identifier metadata
  -> bind same-locale navigation
```

There is no translation-family registry, cross-locale series registry, i18n paginator drop, fallback selector, aligned-window model or collation-provider interface.


## Deliberate exclusions

The feature does not include:

* Locale or identifier extraction from paths and filenames.
* A configured list of locales or generation of empty locale sets.
* Translation-family recognition or validation for paginated items.
* Cross-locale paginator navigation or alternate-page registries.
* Language-switcher, redirect, canonical or `hreflang` rendering.
* Translation fallbacks, shared-content selection or aligned logical windows.
* Inference between translated taxonomy values or route segments.
* Locale-sensitive sorting, alphabetic collation or display-number formatting.


## Open design decisions

The following details should be settled during implementation:

* Final configuration names for the metadata paths and synthetic locale.
* The deterministic raw spelling selected when several values share one canonical locale key.
* Whether locale maps support `default`, and whether a missing entry warns or fails.
* The final set of presentation fields that accept locale maps.
* The exact escaping and separator rules for composed identifiers.
* How invariant output roles are represented when multiple layouts are supported.
* Whether a configured synthetic locale should merge with candidates that explicitly use the same value.
* Whether composed-identifier collisions always fail or may warn in a non-strict mode.

These decisions should preserve the central rule: pv3 partitions by configured metadata, then writes useful general metadata onto every generated index without modelling translations itself.
